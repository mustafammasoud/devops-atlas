# Homepage UX Enhancement — Ops Handbook

## Goal

Improve the existing Ops Handbook homepage so that a first-time visitor immediately understands:

1. What this site is.
2. Where they should start learning.
3. What content is currently available.
4. How large the documentation is.

Do **not** redesign the homepage from scratch. Preserve the existing visual identity, layout language, typography, spacing system, colors, components, responsive behavior, and overall editorial/technical-manual feel.

The result should feel like a natural evolution of the current homepage, not a new website.

---

## 1. Add a "Start Here" section

Add a clear onboarding section near the top of the homepage, after the Hero.

Primary message:

**New to DevOps? Start with the Fundamentals →**

Below it, show the DevOps Fundamentals learning sequence using the existing 9 Fundamentals articles:

1. What is DevOps?
2. Why do we need DevOps?
3. Where does DevOps fit in the software lifecycle?
4. What does DevOps culture mean?
5. How does software move from idea to production?
6. Why should we automate?
7. What are CI and CD?
8. What are environments and infrastructure?
9. How do major DevOps tools fit together?

Use the actual article routes generated by the content system.

### Important

Do NOT hardcode article URLs if they can be derived from the existing content collection/routing system.

The sequence should be generated from the existing Fundamentals content and its metadata/order where possible.

Do not write or modify the educational content of these articles.

The Start Here section should communicate a learning path without becoming a complicated course dashboard.

Keep it visually simple and editorial.

---

## 2. Add "Latest Articles"

Add a **Latest Articles** section.

Requirements:

* Automatically retrieve articles from the content collection.
* Sort them using the existing article metadata/date/order conventions.
* Show approximately 3–4 articles.
* Each item should link to the real article route.
* Display useful metadata such as title, area/tool, and reading time if the existing system already supports it.
* Do not invent article metadata.
* If the current content set is small, gracefully display the available articles rather than creating fake entries.

This section must remain useful as the documentation grows.

Do not manually maintain a list of latest articles.

---

## 3. Add article counts

Make the homepage documentation areas show their article counts.

For example:

```text
Containers
Docker and container technologies
2 articles
```

The count must be calculated dynamically from the Content Collection.

Do NOT hardcode numbers.

The existing homepage should continue showing the curated 8 Documentation Areas:

1. DevOps Fundamentals
2. Operating Systems
3. Networking
4. Version Control
5. Programming & Scripting
6. Containers
7. CI/CD & Automation
8. Container Orchestration

The `/docs` page must continue showing all 14 documentation areas.

Keep the existing **View all →** action exactly as the current primary navigation to the complete documentation index.

Do not add a duplicate "View all" button.

---

## 4. Add a minimal statistics row

Add a small, understated statistics section near the lower part of the homepage.

Use only meaningful dynamically calculated values.

At minimum:

* Total published articles
* Total documentation areas
* Fundamentals articles

Example:

```text
9 Articles     14 Areas     9 Fundamentals
```

These values must be generated from the content/category system.

Do NOT hardcode statistics.

Do not create unnecessary metrics simply for visual decoration.

The statistics should feel like metadata about the handbook, not like a SaaS analytics dashboard.

---

## 5. Homepage structure

The resulting homepage should roughly follow this hierarchy:

```text
Hero
  ↓
Start Here
  ↓
Latest Articles
  ↓
Documentation Areas
  ↓
Statistics
  ↓
Author attribution
```

Preserve the existing author attribution section and social links.

Do not remove or duplicate existing homepage sections unless necessary for the implementation.

---

## 6. Design requirements

Maintain the existing Ops Handbook design language:

* Warm editorial / technical-manual aesthetic.
* No blue.
* No gradients.
* No neon.
* No excessive cards.
* No dashboard-like UI.
* No unnecessary animations.
* No emojis.
* No decorative AI-generated-looking graphics.
* Preserve existing light/dark themes.
* Preserve existing typography.
* Preserve existing responsive behavior.
* Maintain strong readability and restrained spacing.
* Keep the interface feeling human-designed and documentation-oriented.

The new sections should look like they have always belonged to the site.

---

## 7. Architecture requirements

Follow the existing Astro architecture.

Use:

* Astro Content Collections / Content Layer
* Existing utilities such as `src/utils/docs.ts`
* Existing category metadata in `src/data/categories.ts`
* Existing reusable components where appropriate

Prefer extending existing utilities/components over duplicating logic.

Avoid unnecessary new abstractions.

Do not introduce:

* React
* Next.js
* a backend
* a database
* a CMS
* authentication
* new external services
* new dependencies

Unless an existing project dependency is already required, this task should not add dependencies.

---

## 8. Content ownership rule

The documentation content itself is written and maintained by the site owner.

Therefore:

**Do not write, rewrite, expand, summarize, or invent educational article content.**

Only modify homepage presentation, data selection, metadata handling, and UI where necessary.

---

## 9. Empty / future-state behavior

The site is intentionally still growing.

Make sure the homepage remains graceful when:

* There are only a few articles.
* An area has zero articles.
* More articles are added later.
* More tools are added later.
* Fundamentals grows or changes.

Avoid hardcoded assumptions that will make the homepage brittle.

---

## 10. Validation

After implementation, run:

```bash
npm run check
npm run build
```

Verify:

* No TypeScript/Astro errors.
* No broken routes.
* Start Here links point to real Fundamentals articles.
* Latest Articles are generated dynamically.
* Article counts are accurate.
* Statistics are accurate.
* `/docs` still contains all 14 areas.
* Homepage still contains only the curated 8 areas.
* Existing View all → remains unchanged.
* Light mode works.
* Dark mode works.
* Mobile layout works.
* No localization/language-switcher functionality is reintroduced.
* Arabic/RTL article support remains intact.

Finally, report:

1. Files changed.
2. What was implemented.
3. Any architectural decisions.
4. `npm run check` result.
5. `npm run build` result.
6. Any issues or follow-up concerns.

Do not make unrelated changes.
